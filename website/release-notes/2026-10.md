## Web app
- Added the "What's new" panel: the release notes, newest first, with a search box. The link `/#whats-new` opens it, handy to share in a chat.
- The "What's new" dialog pops up once a month (or quarter) is over, with everything that changed in it. The notes of the current month show in the panel as a preview, tagged "In progress".
- The sidebar's help button opens the new [user guide](/docs/user-guide/overview).
- The Logs view lets you filter runs (all, failed, running), tags failed runs with the reason (e.g. "LSF: out of memory"), and stays fast with hundreds of runs.
- In the Logs view, each run fits on one line, with its configuration in short and buttons to open its output directory, redo, mark as failed or delete it. The full configuration shows when you open the run's logs, and the logs no longer get wider than the window.
- The sidebar's Logs entry shows how many runs failed, or are still running.
- Switch between a run's `log.txt`, `log.lsf.txt` and `log.dask.txt`. For LSF runs, a summary shows the exit reason, host, run time and memory used vs requested, with hints that point to the batch's `lsf:` options.
- Batches started from QA-Board (tuning, "Run Tests") show whether `qa batch` is waiting for LSF, running, failed (with the error) or didn't start any run, with a link to its logs.
- Follow links to code, commits and branches on your project's own git host, with the right URLs for GitHub, GitLab, Gitea/Forgejo and Bitbucket, instead of a hardcoded GitLab server.
- Shows the "Quotas" links only when the server has a quota dashboard.
- The error page links to your server's support page.
- Commit pages with thousands of outputs are much faster: filtering, sorting and matching outputs with their reference no longer freeze the page, and filters respond as you type. Large metric tables render only the rows on screen.
- The URL now keeps everything you select: the commit list's date range, the metrics shown in tables, the commits highlighted on the History page. Share the link, reload, or use the back button: you get the same view. Typing filters and toggling viewer options no longer adds entries to the browser's history.
- Pages you already visited show up instantly when you come back, then refresh in the background. Commits with running outputs keep updating.
- Visualizations download their files as they scroll into view, and files shared by several cards or viewers are downloaded only once. Batches with more than 300 runs show more cards as you scroll, or all of them with "show all".
- The History page links back to the branch's commits, and its "vs reference" table has a title.
- Plots of SLAM results can no longer be uploaded to Plotly's public cloud.
- Start the GitHub Actions workflows declared in your project's `qaboard.yaml` from the Integrations menu, and follow the run you started, even when GitHub ran it on a newer commit of the branch. Only users who can access the project can see or start them ([GitHub Actions](/docs/triggering-third-party-tools#start-github-actions-workflows)).
- See the status of a GitHub Actions workflow's latest run for the commit, with a link to it, in the Integrations menu.
- See your git host's defaults in the Integrations menu of branch pages, when your project configures none and QA-Board knows its git host: GitLab's pipeline status, or a link to GitHub Actions ([default integrations](/docs/triggering-third-party-tools#default-integrations)).
- Hides the Integrations menu's badges that fail to load, e.g. for private projects or projects without CI.
- See commit authors' avatars from GitHub, Gitea/Forgejo and Bitbucket, learned from push events, or else their Gravatar.
- Loads avatars and badges from public git hosts (github.com, Bitbucket, Codeberg, and your server's git hosts that aren't GitLab) directly, which is faster. The others, and Gravatars, still load through the server, which can reach hosts you can't.
- Search all of a project's commits from the commit list's **Filter...** box, not only those in the date range: by message, committer, branch, batch or hash. Use `branch:`, `committer:`, `batch:`, `message:` or `id:` to look at one field, and `-word` to exclude ([searching commits](/docs/user-guide/finding-results#searching-commits)).
- Scroll through long commit lists: they show the 50 latest commits, then more as you scroll, so big projects open much faster. Branch pages still get their whole date range at once (up to 1000 commits), for their metrics chart.
- Click **Older commits** at the end of the commit list to look a week further back.
- Open the projects list much faster on sites with hundreds of projects: it downloads less, and shows more projects as you scroll.
- Jump to a branch from the **Filter...** box: when your search can be a branch name (one word, or a `branch:` term), it suggests the most recently active branches that match, even in projects with thousands of branches.

## CLI and project setup
- At SIRC, upgrading `qaboard` now requires also installing `qaboard-site-sirc`, see the [installation instructions](/docs/installation). Site packages provide a base `qaboard.yaml` that every project's configuration is merged on ([site defaults](/docs/project-init#site-defaults)): `qa init` shows the inherited values instead of overriding them.
- LSF runs write their output live to `log.lsf.txt`, with LSF's job report at the end. `qa batch` no longer passes an LSF queue or project when none is set, and fails fast when `bsub` is missing.
- `qa init` creates a configuration that runs locally: LSF is commented out, and storage defaults to `/mnt/qaboard` like the server.
- The CLI reads your `QA_TOKEN` from `$QA_TOKEN` or `~/.qaboard/secrets.yaml`, and warns if other users can read that file.
- `QABOARD_API_VERIFY` controls the TLS verification of the CLI's requests to the server: `true` (the default), `false`, or the path to a CA bundle.
- Site packages (company-specific plugins) are no longer ignored on Python 3.8 and 3.9.
- The package now includes the `qatools` compatibility package, and update checks no longer suggest a site-specific install command to everyone.
- `qa batch` sets a commit status that links to the results on GitHub too ([CI integration](/docs/ci-integration)).
- `qa check-bit-accuracy` waits for the GitHub checks of the reference commit too, like it does for GitLab pipelines ([bit-accuracy](/docs/bit-accuracy)).
- In GitHub Actions, `qa` records the pull request's branch and last commit instead of the temporary merge commit ([CI integration](/docs/ci-integration#example-with-github-actions)).
- In GitHub Actions, `qa` records the tag of tag builds.
- `qa` finds your git host, its API and its token in `QABOARD_GIT_HOSTS` too ([git hosts](/docs/backend-admin/git-hosts#the-cli)).
- `qa` sends `GITHUB_ACCESS_TOKEN` only to github.com and the GitHub hosts you configured, not to any hostname that looks like GitHub.

## Server and administration
- Zero-downtime deploys with [deployments/deploy.py](/docs/backend-admin/deployment): images tagged per version, several backend replicas behind nginx, rolling updates, `rollback`, `status` and `restore-db`.
- `deploy.py seed-db` fills a staging database with only production's recent data.
- A [Helm chart](/docs/backend-admin/kubernetes) to run QA-Board on Kubernetes.
- The backend has a `/api/v1/health` endpoint, shuts down gracefully, and keeps working when redis is down.
- Security: actions that run commands (redo, tuning, stopping or deleting batches...) now require a login and run as the logged-in user, and their inputs are escaped. See SECURITY.md.
- Security: the server only writes, deletes or runs code in the folders listed in `QABOARD_STORAGE_ROOTS` (default: `/mnt/qaboard`), and refuses results stored elsewhere. **If your projects store results in other folders, set it before upgrading** (see [environment variables](/docs/deploy#optional-environment-variables)).
- Require a secret in push webhooks: set `QABOARD_WEBHOOK_SECRET`, and the same secret in your repositories' webhooks, so that only your git hosts can send push events ([webhooks](/docs/backend-admin/git-hosts#webhooks)).
- Each batch started from QA-Board gets its own folder with its scripts and logs, under the batch's `qaboard-batches/`.
- The web app links to the docs served by your server at `/docs/`, which match its version, instead of the public website. Set `QABOARD_DOCS_ROOT` to use another docs site.
- Configure the quota dashboard and support links with `QABOARD_QUOTA_URL_TEMPLATE` and `QABOARD_SUPPORT_URL`.
- Configure all your git hosts (GitHub and GitHub Enterprise, GitLab, Gitea/Forgejo, Bitbucket, other git servers), each with its own token and webhook secret, with `QABOARD_GIT_HOSTS` ([git hosts](/docs/backend-admin/git-hosts)).
- Keeps your current git settings working: `GITLAB_HOST` (also without a scheme, or with credentials), `GITLAB_ACCESS_TOKEN`, `GITHUB_ACCESS_TOKEN`, `QABOARD_GITHUB_HOSTS` for GitHub Enterprise, and `QABOARD_GITLAB_HOSTS`, whose hostnames are other names of `GITLAB_HOST`. A GitLab and a GitHub host can share a hostname ([backward compatibility](/docs/backend-admin/git-hosts#backward-compatibility)).
- Records each existing project's git host, with a migration that uses the deploy's git host settings. **Before upgrading, keep `GITLAB_HOST` set**, or list your GitLab in `QABOARD_GIT_HOSTS` with the hostnames older projects used ([upgrading](/docs/backend-admin/git-hosts#upgrading-from-older-versions)).
- Receives the push events of repositories on Gitea, Forgejo and Bitbucket Cloud, at `/webhook/gitea` (or `/webhook/forgejo`) and `/webhook/bitbucket` ([webhooks](/docs/backend-admin/git-hosts#webhooks), [project setup](/docs/project-init#optional-connect-your-git-host)).
- Stops saving git tokens in new clones' `.git/config`, or showing them in error messages: git gets them from a credential helper, and only for their own host (it needs git 2.31 or newer). Clones made by older versions still have the token in their remote URL: [remove it](/docs/backend-admin/git-hosts#tokens).
- Stops sending git tokens, and GitLab session cookies, to another host when git or API calls are redirected there.
- Reads git tokens and webhook secrets only from its environment, not from the CLI's shared secrets file (`QA_SECRETS`).
- Refuses push events for git hosts without a webhook secret, once any host has one or `QABOARD_WEBHOOK_SECRET` is set (`401`): otherwise anyone could claim a repository is on such a host.
- Refuses push events from git hosts the server doesn't know (`403`), without reading the rest of the payload. Pushes to `/webhook/gitlab` from unknown hostnames still go to your GitLab, like before.
- Refuses push events that would move an existing project to another git host (`409`).
- Refuses webhook payloads over 25 MB (`413`), the most GitHub sends.
- Answers and ignores webhook events other than pushes, like GitHub's `ping`.
- Keeps starting, and running migrations, when the git host settings are invalid: the server logs the error, and refuses webhooks (`503`) until you fix them.
- Lists of commits answer many times faster on big projects, and use much less memory: they no longer load every output of every commit.
- API: page through `/api/v1/commits` with `limit` and `offset` (the `X-Has-More` response header tells if there are more), and search all of a project's commits with `q` ([lists of commits](/docs/apis#lists-of-commits-branches-and-projects)). Without them, it answers as before.
- API: get the most recently active branches matching a text with `/api/v1/project/branches?q=...&limit=...`.
- API: get a much smaller list of projects with `/api/v1/projects?summary=true`.
- Adds two indexes on `ci_commits`, to list commits faster. They are built without blocking writes, which can take a few minutes on big databases. If building one fails, the next deploy builds it again.
- Starts even when the database has migrations it doesn't know, made by a newer version, e.g. after a rollback: it keeps them.
- Versions from before October 2026 don't start on a database migrated by this one: to roll back to them, first undo the newer migrations ([rollbacks](/docs/backend-admin/deployment)).
- The Helm chart's migrations Job gets the chart's `config:` settings, which data migrations need ([Kubernetes](/docs/backend-admin/kubernetes)).

## Fixes
- With LSF job arrays and the Dask runner, `qa run` no longer deletes the log file its output goes to: errors are no longer lost.
- The tuning form shows a readable error instead of the server's raw response.
- A stuck run's "Mark as Finished" action is now labelled "Mark as Failed", which is what it does.
- Security: marking a run as failed or deleting it now requires a login.
- Deleting results no longer deletes the contents of folders that they link to.
- The Improvement report showed "=" for metrics that changed, and badges for those that didn't.
- Outputs are compared with reference runs from the same platform first.
- Selecting a milestone from `qaboard.yaml` selects the latest commit of its branch.
- Auto-ROIs on image diffs work again, and ROI thumbnails use the right image server.
- In point clouds, WASD moves while the key is pressed, not after it's released.
- The tuning form remembers the "Overwrite" option, and setting the number of iterations no longer crashes.
- On the History page, picking metrics updates the metrics distribution too.
- Moving runs to another batch closes the dialog, and saving a milestone no longer risks losing it.
- Text viewers set to show only differences hide identical files, and videos play without a reference.
- Repositories whose clone is broken are cloned again, instead of failing until an admin deletes them. The broken clone is only replaced once the new clone succeeded.
- The server only deletes the git clones it made: it refuses repository paths inside a clone, or that hold other clones.
- Tag pushes record the tag's whole name: its first character was cut.
- `bit_accuracy.on_reference_failed_ci: compare-first-parent` goes back up to `bit_accuracy.max_parents_depth` parents, instead of two at most.
- `bit_accuracy.failed_ci_job_name` works again: `qa check-bit-accuracy` only looks at that job (`<job> <subproject>` in subprojects).
- `qa check-bit-accuracy` counts skipped CI jobs as successful, instead of waiting for them.
- Servers outside SIRC no longer show avatars from SIRC's directory for GitLab users without one: set `QABOARD_AVATAR_URL` to use your own ([environment variables](/docs/deploy#optional-environment-variables)).
- Commit rows show the main metric of their CI batch again (median and average).
- Branch pages plot metrics over time again.
- Stopping a batch whose runs can't be stopped reports the error instead of failing.
- The "No projects yet" page links to your server's docs and support page.
