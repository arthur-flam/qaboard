## Web app

### Tuning
- Set up an automated tuning with a guided form: in **Run Tests / Tuning**, choose **Search automatically**, give the parameters and their ranges, the metrics to improve (any your runs return) and a budget it recommends. It checks your settings as you type, and the YAML stays one click away ([find the best parameters automatically](/docs/user-guide/automated-tuning)).
- Read what any tuning found in **Tuning Analysis**, automated or a grid: the best parameters, how much each matters, the best trade-offs, and new parallel coordinates. **What this tells you** says whether more evaluations would help; continue the search or turn a grid into one in a click ([tuning analysis](/docs/user-guide/running-from-the-webapp#tuning-analysis)).

### Exports and scripts
- See every file's name before you export: short, readable names instead of hashes, that say only what tells files apart, e.g. `night_street__v1.2.png`, colored by what each part says, with one-click fixes when two files would get the same name ([export files](/docs/user-guide/sharing#exporting-files), [names](/docs/user-guide/sharing#export-names)).
- Lay files out your way, in one folder, in new and reference folders for a diff tool or like the inputs, saved as [presets](/docs/user-guide/sharing#export-presets). Export crops of the regions of interest, the references cropped at the same place, and find your exports in **Storage usage → Exports** ([crops](/docs/user-guide/sharing#export-crops)).
- Work on the runs you see from a script: **Script**, next to **Export**, shows a Python snippet or shell command for them. Metrics a script added later get a pencil mark saying who added them and when ([runs in a script](/docs/user-guide/sharing#runs-in-scripts), [added metrics](/docs/user-guide/metrics#added-metrics)).

### Metrics and reference runs
- See every metric your runs return, declared or not, in the Summary, the tables, the run cards and the History page. When QA-Board doesn't know whether higher or lower is better, changes are gray or blue, never green or red, and hovering says why ([metrics](/docs/user-guide/metrics#summary)).
- Compare runs on different inputs without ids, like a register sweep's captures: the **Reference runs** row suggests the change of name that pairs them, e.g. `reg0x1A=05 → 03`, applied in one click and kept in the page's link ([pair by name](/docs/user-guide/reference-runs#pair-by-name)).
- Pick another reference run from the tag next to a run's name, or turn your pick into a rule for every run, like preferring reference shots with `unit = 2` ([pick another](/docs/user-guide/reference-runs#pick-another)).

### Viewers
- Click a pixel to pin and copy its values, in images and videos. **Where they differ** finds differences of a given size, regions of interest are outlined with their labels, and the annotations made in your annotation app show on the run's input. With raw images, drag on the histogram to highlight a range of values ([image viewer](/docs/user-guide/image-viewer#pixel-values)).
- See a run's benchmarks next to the reference's, and whether each change is beyond the noise, and find what got slower in a differential flame graph, with a table of the top functions, search and keyboard navigation ([benchmarks](/docs/user-guide/other-viewers#benchmarks), [flame graphs](/docs/user-guide/other-viewers#flame-graphs)).

### Commit page
- See each test open on what matters for it: in projects that set it up, a run's card shows its own visualizations and opens its images in their own mode. Pick **Compact** run cards for one line per run, like the logs ([view options](/docs/user-guide/commit-page#view-options)).
- Tell runs apart when they come from several batches or databases: names start with them, e.g. *night › kitti › 0001.png*, and runs are grouped by batch. Hover a run's name in the logs and tables to see its History, batch, input and metadata ([run cards](/docs/user-guide/commit-page#run-cards)).
- Deal with failed runs: **Show only the failed runs** filters the page to them (`status:failed`). Runs done again are tagged **attempt 2**, **attempt 3**..., with who ran the earlier attempts and how they ended ([the commit page](/docs/user-guide/commit-page)).

### Across the web app
- Tell your tabs apart: they're named after what they show and count pending and failed runs, and copied links paste as the page's name in Teams, Outlook or Confluence. When part of a page crashes, the rest stays, and **Try again** gets you back ([sharing](/docs/user-guide/sharing#links-are-shareable)).
- Find where pending runs come from: click a batch, commit, branch, queue, runner or user in **Runs activity** to see only its runs, or look at one person's with **Someone…**. It loads 3 to 9 times faster on busy servers ([runs activity](/docs/user-guide/runs-activity#find-where-runs-come-from)).
- Set quality gate rules no commit can change, as a project's owner, in the project's **Admin → Quality gate**, and decide whether a commit that loosens its own rules fails. **Access** moved under **Admin** ([project gate rules](/docs/user-guide/project-gate)).

## CLI and project setup

- **Before you upgrade**:
  - Upgrade `qaboard` together on the machines that start batches and those that run them: older versions save a run that is done again in another folder.
  - Shared and CI runs done again now get a new folder, `<run>_attempt2`...: scripts that build run paths themselves must read the first folder's *latest_attempt.txt*, or keep `outputs: {reruns: in-place}` ([reruns](/docs/storage/where-is-the-data#reruns)).
  - Text outputs are hashed with Unix line endings everywhere, and `.hex` files are text again: record references with Windows line endings again once, or mark them `bit_accuracy.binary` ([line endings](/docs/bit-accuracy#line-endings)).
  - In metrics files, `smaller_is_better: null` (or empty) now means neither is better, it used to mean smaller: write `true` where you meant it.
  - `qa optimize` no longer reads `solver` (scikit-optimize): it says what to write instead ([solver](/docs/auto-optimization#solver)).

### Metrics and tuning
- Declare metrics where your code computes them: return `Metric(value, suffix=" ms", smaller_is_better=True)`, call `define_metric()`, or write a *metrics_definitions.json* from any language. The web app and `qa gate` use them, and your metrics file keeps working ([declaring metrics](/docs/computing-quantitative-metrics#declaring-metrics)).
- `qa optimize` searches with Optuna, and is no longer experimental: say which way is better (`ap_small: max`), resume a tuning by running it again, start evaluations as soon as one ends, stop early, and find the best trade-offs with `pareto: true` ([automated tuning](/docs/auto-optimization#objective)).

### Runners
- Run batches on Kubernetes with the `kubernetes` runner: each run is a pod of a Job, as your own user, with your shared storage and within your cluster's quotas, and `runs_per_pod` keeps GPU pods busy with short runs. When pods wait, `qa batch` says why ([Kubernetes](/docs/kubernetes-runner)).
- Start Dask workers on Slurm, PBS, SGE, HTCondor, OAR, Moab or Kubernetes, not only LSF (`runners.dask.cluster.type`), and stop Celery batches with Ctrl+C. Celery runs start from the worker's environment, e.g. its `CUDA_VISIBLE_DEVICES` ([Dask](/docs/dask-integration#other-schedulers), [Celery](/docs/celery-integration#secrets)).
- Check everything a batch needs with `qa doctor`: *qaboard.yaml*, the server, the storage and the runner's permissions, with how to fix each problem. `--test-job` also starts a small job ([qa doctor](/docs/doctor)).

### Scripts, agents and the HTTP API
- Get the runs a web app page shows with `qaboard.runs(url)`, or by project, commit, batch and filter, with their metrics and files, and add metrics or files after the fact with `run.log_metrics()` and `run.log_artifact()`. `import qaboard` no longer reads *qaboard.yaml* or git ([runs in scripts](/docs/apis#runs-in-scripts)).
- Read results from any language: the server describes its HTTP API at `/api/v1/openapi.json`, and `/api/v1/docs` tries requests. The `qaboard-integration` and `qaboard-results` skills teach coding agents to wrap a project and compare runs with the reference ([HTTP API](/docs/http-api), [agents](/docs/agents)).

### CI and the quality gate
- Get the gate's verdict on the pull request: `qa gate --post-comment github` (or `gitlab`) posts one comment, updated on each push and shared by every gate job. Write rules per `qa batch` or label (`gate.batches` is now `gate.labels`, the old name works) ([the gate on pull requests](/docs/quality-gate-pull-requests), [scopes](/docs/quality-gate#scopes)).
- Send results from GitHub Actions or GitLab CI without storing a token: click **Trust CI jobs** in a service account's **Tokens** and copy the configuration it shows. `qa` exchanges the job's ID token for a short-lived token ([CI without a secret](/docs/ci-integration#ci-without-secrets)).

### Benchmarks, flame graphs and usage events
- Bring benchmarks and profiles in with your tools' own files: list them in `outputs.visualizations`, and `benchmark_metrics(path)` makes each benchmark a metric. `save_flame_graph()` converts `perf script` and pprof ([benchmarks](/docs/benchmarks), [flame graphs](/docs/flame-graphs)).
- `qa` tells your server which commands people run, outside CI only, in the background; `QA_NO_ANALYTICS=1` turns it off ([usage analytics](/docs/backend-admin/usage-analytics)).

## Server and administration

- **Before you upgrade**:
  - After the upgrade, back up the encryption key the server generates when a secret is first saved in **Admin → Settings**, or set `QABOARD_ENCRYPTION_KEY`: database backups don't include it ([back up the key](/docs/backend-admin/settings#back-up-the-key)).
  - Rules on the runs of one `qa batch` need this server version: older servers make them undecidable.
  - Scripts calling `/api/v1/export` keep working, but it's deprecated: its answers carry a `Deprecation` header to find them ([exports](/docs/backend-admin/storage#exports)).

### Settings and accounts
- Change most settings in **Admin → Settings**, without a deploy: git hosts, Jenkins, email, the web app's links... Each says where its value comes from, **Save it here** moves it out of the environment, and secrets are encrypted in the database ([settings](/docs/backend-admin/settings)).
- Set up a new server from the web app with the setup token from the backend's logs, create local accounts and reset passwords in **Admin → Users**, and keep profiles and pictures up to date from sign-in, also from Microsoft Graph ([the first admin](/docs/backend-admin/user-management#the-first-admin), [profiles](/docs/backend-admin/sign-in#pictures-and-profiles)).
- Tokens that CI jobs exchange last 6 hours, and the server must reach the CI's issuer. Projects' owners can trust GitHub, GitLab.com and your git hosts; other issuers need an admin ([service accounts](/docs/backend-admin/user-management#service-accounts)).

### Runners
- Let users start, redo and stop batches on Kubernetes from the web app, as themselves, with the Helm chart's `runners.kubernetes`, one namespace per team. With `local` or `celery`, the server's secrets stay out of users' batches, but their code runs in the server's container ([Kubernetes](/docs/backend-admin/kubernetes#start-batches-from-the-web-app), [security](/docs/backend-admin/runners#security)).

### Usage and integrations
- See how QA-Board is used in **Admin → Usage**: active people in the web app and the CLI, what they look at and start, per user, group and project, with CSV exports and SQL views for Metabase. The overview lists what to configure next ([usage analytics](/docs/backend-admin/usage-analytics)).
- Show another app's annotations in the image viewer with a Python package that provides an annotation source ([annotation sources](/docs/backend-admin/annotations)). Deploy smaller images: the backend drops its compilers (2.2 GB → 1.4 GB) and the docs image is 40 MB instead of 1.3 GB.

## Fixes
- **Storage usage** no longer crashes going from Batches to Commits, projects named like `team/access/tools` open, renaming a reference works, `/` and `?` type in code editors in Chrome and Edge, and large batch files with YAML anchors no longer freeze **Available Tests**.
- `qa batch` with LSF no longer gets stuck when started from a Docker container, or crashes when killed runs left a corrupt `metrics.json`, and `qa gate` no longer waits for the reference's tuning iterations.
- Batches the web app starts with the `local` or `celery` runners are no longer killed after 5 minutes, and an invalid `JENKINS_AUTH` or `GITLAB_AUTH` no longer stops the server from starting ([runners](/docs/backend-admin/runners#local)).
- Export copies files you read through a group, and checks first that you can write the folder; **Export (legacy)** exports real folders, not links Windows can't open ([users' accounts](/docs/backend-admin/user-management#users-accounts)).
