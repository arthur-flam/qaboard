## Web app

### Tuning
- Set up an automated tuning with a guided form: in **Run Tests / Tuning**, choose **Search automatically**, give the parameters and their ranges, the metrics to improve (any your runs return) and a budget it recommends. It checks your settings as you type, and the YAML stays one click away ([find the best parameters automatically](/docs/user-guide/automated-tuning)).
- Read what any tuning found in **Tuning Analysis**, automated or a grid, a sampling or values tried by hand: the best parameters and how much each matters, the tests where they lose, the best trade-offs between metrics, and new parallel coordinates to follow every parameter set ([look at the results](/docs/user-guide/running-from-the-webapp#tuning-analysis)).
- Know what to do next: **What this tells you** says whether more evaluations would help and which best values sit at the edge of their range. Continue the search, run the best parameters on other tests, or turn a grid into a search in one click. Runs without metrics get a script that scores them ([score the runs](/docs/user-guide/running-from-the-webapp#score-runs)).

### Metrics
- See every metric your runs return, declared or not, in the Summary, the tables, the run cards and the History page. Without configuration, the Summary shows the 8 metrics that changed the most ([metrics](/docs/computing-quantitative-metrics#what-qa-board-shows-by-default)).
- Trust the colors: when QA-Board doesn't know whether higher or lower is better, changes are gray or blue, never green or red, and hovering a metric says why ([user guide](/docs/user-guide/metrics#summary)).

### Image viewer
- Click a pixel to pin its values and copy them, in images and videos, in decimal or hexadecimal ([pixel values](/docs/user-guide/image-viewer#pixel-values), [in videos](/docs/user-guide/video-viewer#pixel-values)).
- Find differences of a given size with **Where they differ**, also in all the runs, e.g. small defects next to a large change. Regions of interest are outlined with their labels: click one to zoom on it ([find where images differ](/docs/user-guide/image-viewer#find-where-images-differ)).
- See the annotations people made on a run's input in your annotation app, when your server is connected to one: outlined on the images, with a link to each ([annotations](/docs/user-guide/image-viewer#annotations)).
- Work with raw images: **Guess from the view** applies its CFA guess, and dragging on the histogram of **Image values** highlights a range of raw values, per sensor channel ([raw images](/docs/user-guide/image-viewer#image-values)).

### Commit page
- See each test open on what matters for it: in projects that set it up, a run's card shows its own visualizations and opens its images in their own mode ([view options](/docs/user-guide/commit-page#view-options)).
- Tell runs apart when they come from several batches or databases: their names start with them, e.g. *night › kitti › 0001.png*, and they're grouped by batch. Sort runs by batch, database, status or configuration too ([run cards](/docs/user-guide/commit-page#run-cards)).
- Pick **Compact** run cards, one line per run like the logs, and hover a run's name in the logs and tables to see its History, batch, input and metadata ([logs](/docs/user-guide/logs#reading-a-log)).
- Deal with many failed runs at once: **Show only the failed runs** filters the page to them, with the new `status:failed` filter, instead of a long list above the results ([the commit page](/docs/user-guide/commit-page)).
- Read less: text diffs fold the unchanged lines ([text diffs](/docs/user-guide/other-viewers#text)), and a click shows long settings, like whole commands, in full ([read configurations](/docs/user-guide/comparing-results#reading-configurations)).

### Running tests
- See where a batch is defined at a glance: **Run Tests / Tuning**, **Available Tests** and the **Logs** name each batch file once, e.g. *Defined in qa/batches.yaml*, and a click opens it at the commit ([running tests](/docs/user-guide/running-from-the-webapp#running-tests-and-tuning)).

### Tabs, links and errors
- Tell your tabs apart: they're named after what they show, and count pending and failed runs. Ctrl/Cmd+click opens the sidebar's views in a new tab, and the **link** button copies a link that pastes as the page's name in Teams, Outlook or Confluence ([sharing](/docs/user-guide/sharing#links-are-shareable)).
- Keep working when part of a page crashes: the rest of the page stays, a code editor keeps your text, and you get back with **Try again**. The error page says when the maintainers were told, or opens a filled-in report ([report a bug](/docs/user-guide/sharing#bug-reports-and-support)).

### Runs activity and usage
- Find where pending runs come from: click a batch, commit, branch, queue, runner or user in **Runs activity** to see only its runs, and list the runs pending for over a day to mark them failed ([runs activity](/docs/user-guide/runs-activity#find-where-runs-come-from)).
- Look at one person's runs with **Someone…** in **Storage usage** and **Runs activity** ([storage usage](/docs/user-guide/storage-usage#find-what-takes-space)), and at your own usage of QA-Board in **Settings → Activity**.

## CLI and project setup

### Metrics and visualizations
- Declare metrics where your code computes them: return `Metric(value, suffix=" ms", smaller_is_better=True)`, call `define_metric()`, or write a *metrics_definitions.json* from any language. The web app and `qa gate` use them ([declaring metrics](/docs/computing-quantitative-metrics#declaring-metrics), [quality gate](/docs/quality-gate#rules)).
- Keep your metrics file while you move: the fields from your code win. **Check yours**: `smaller_is_better: null` (or empty) now means neither is better, it used to mean smaller: write `true` where you meant it ([metrics files](/docs/computing-quantitative-metrics#declaring-metrics-in-a-metrics-file)).
- Say what each test shows by default with a `view` mapping in a batch's configurations or an input's metadata: its visualizations and how its images open ([per-test views](/docs/visualizations#per-test-views)).

### Automated tuning with `qa optimize`
- `qa optimize` searches with Optuna instead of scikit-optimize, which isn't maintained anymore, and is no longer experimental. Configurations keep working except `solver`: it says what to write instead ([from scikit-optimize](/docs/auto-optimization#scikit-optimize), [solver](/docs/auto-optimization#solver)).
- Say which way is better in the objective (`ap_small: max`), resume a tuning by running it again, start evaluations as soon as one ends with `parallel_sampling`, stop early, and look for the best trade-offs with `pareto: true` ([the objective](/docs/auto-optimization#objective), [resume](/docs/auto-optimization#resume), [configuration](/docs/auto-optimization#configuration)).

### Bit accuracy and usage events
- Compare text outputs between Linux and Windows: `qa` hashes text files with Unix line endings everywhere, and `.hex` files are text again. If your references have text outputs with Windows line endings, record them again once, or mark them `bit_accuracy.binary` ([line endings](/docs/bit-accuracy#line-endings)).
- `qa` tells your server which commands people run, outside CI only, in the background; `QA_NO_ANALYTICS=1` turns it off ([details](/docs/backend-admin/usage-analytics)).

## Server and administration

- **Before you upgrade**:
  - Upgrade `qaboard` together on the machines that start batches and those that run them: versions from before this one save a run that is done again in another folder ([when things go wrong](/docs/storage/where-is-the-data#reruns)).
  - Rules on the runs of one `qa batch` need this server version: older servers make them undecidable.

### Usage analytics
- See how QA-Board is used in **Admin → Usage**: active people in the web app and the CLI, what they look at and start, per user, group and project, with CSV exports and SQL views for Metabase. Turn it off with `analytics.enabled` ([usage analytics](/docs/backend-admin/usage-analytics)).
- **Get more from QA-Board**, on the admin overview, lists what isn't configured yet, like email, single sign-on, webhooks, Sentry or a storage cleaning schedule. **Active in the last 30 days** now counts the people who used QA-Board, not only those who signed in.

### Integrations and deployment
- Show another app's annotations in the image viewer with a Python package that provides an annotation source ([annotation sources](/docs/backend-admin/annotations)). Sentry events from the web app carry the username, the part of the app that crashed and the user's notes ([monitoring](/docs/backend-admin/monitoring)).
- Deploy smaller images: the backend drops its compilers (2.2 GB → 1.4 GB) and the docs image is 40 MB instead of 1.3 GB. The proxy moves to Debian 12. If you build with `development.yml`, it now builds the `dev` stages, which keep the compilers.

## Performance
- **Runs activity** loads 3 to 9 times faster on busy servers: with everyone's runs on a server that runs 80,000 a day, 0.7 s instead of 2.2 s for the last 24 hours.

## Fixes
- **Storage usage** no longer crashes going from Batches to Commits, its bars show each person's share of the total, and it and **Runs activity** no longer show your numbers under **Everyone's** while loading. **Runs activity** says why it couldn't load, and its submenu opens next to the sidebar.
- Projects named like `team/access/tools` open, runs without a default metric sort by name again, renaming a reference works, `/` and `?` type in code editors in Chrome and Edge, and large batch files with YAML anchors no longer freeze **Available Tests**.
- `qa batch` with LSF no longer gets stuck when started from a Docker container, and no longer crashes when killed runs left an empty or corrupt `metrics.json`: those runs are marked failed.
- An invalid `JENKINS_AUTH` or `GITLAB_AUTH` no longer stops the server from starting, Jenkins servers without CSRF crumbs no longer need one, and the backend image upgrades `qaboard` behind a proxy whose CA you install with `CA_CERT_URL`.
