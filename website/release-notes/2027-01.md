## Web app
- Find who started a batch, redid or deleted runs, edited a run's metrics or changed milestones and roles in a project, as its developer or owner, in the project's **Admin → Audit log**, or from a batch's menu ([project audit log](/docs/user-guide/project-audit-log)).
- Tell at a glance what changed on the commit page: in the dark theme the results' cards stand out from the page, metrics turn red only when they miss their target, the image viewer's secondary tools show when you point at it, and the collapsed View options label their sections ([commit page](/docs/user-guide/commit-page)).
- Allow AI assistants such as Open WebUI to read QA-Board as you, read-only, and revoke them in **Settings → Connected apps** ([allowing apps](/docs/user-guide/account#allowing-apps)).

## CLI and project setup
### Upgrading
- `qa` needs Python 3.11 or newer: on older Pythons, `pip install --upgrade qaboard` keeps the last version that supports them. Check your CI runners, cluster nodes and projects' virtual environments with `python3 --version`, and recreate the older ones, e.g. `uv venv --python 3.11` ([installation](/docs/installation#install)).
- Install `qa` lighter: it no longer installs scikit-learn and simplejson. Tuning searches give the same combinations as before. If your project's code imports them, add them to its own requirements.

### Scripts and terminals
- Parse `qa`'s results in scripts and coding agents: `qa batch`, `qa doctor`, `qa auth status` and `qa version` take `--json`, which prints one JSON document on stdout and the rest on stderr, with the same exit codes. `qa batch --list-batches` names the batches, and `qa batch --json` gives each run's id and metrics ([JSON for scripts and agents](/docs/using-the-qa-cli#json-output)).
- Complete `qa`'s commands, options, batch names and `--input` paths in bash, zsh, fish or PowerShell: run `qa completion install` once. It reads your project's files, never the server, and `qa --help` starts about twice as fast ([shell completion](/docs/using-the-qa-cli#shell-completion)).
- See what `qa` does when it surprises you: `qa -v` logs the qaboard.yaml, project, commit, server and storage it found, its runners and uploads, `qa -vv` each request to QA-Board with its status and duration, without tokens. `QA_LOG_LEVEL` does the same in CI, `--log-file` keeps them in a file ([debug what qa does](/docs/using-the-qa-cli#debug-what-qa-does)).
- See what went wrong and how to fix it: `qa` says `error:`, `warning:` and `hint:` with the value involved, for an invalid *qaboard.yaml* (its line), a mistyped command or option (what you likely meant), an unknown batch (the closest names), a server it can't reach (once), a refused token, a failed run. Tracebacks are for bugs, or with `qa -v` ([troubleshooting](/docs/installation#troubleshooting)).
- Read how a batch went at the end of `qa batch`: how many runs passed or failed, and the failed runs' logs.

### Coding agents
- Connect coding agents and chat clients to QA-Board with `qa mcp`, experimental and read-only: they find what you ran lately, compare a commit with its reference, explain failures, follow metrics over commits, look at outputs next to the reference's by type (images, benchmarks, flame graphs, series, JUnit reports), and give you links, including to a tuning filled in for you to start ([MCP server](/docs/mcp)).
- Read where a run is from its id: `GET /api/v1/output/<id>` gives its project, commit and batch. Tokens with only the `read` scope can ask where two images or videos differ ([HTTP API](/docs/http-api)).

### Project setup
- Start a project with fewer edits: `qa init` ignores `output/` in git, uses `main` when it can't ask your git host, and `qa doctor` says when the server won't show the files in your `storage`, and how to send them instead ([project init](/docs/project-init), [uploads](/docs/storage/uploads)).
- Run `.venv/bin/qa batch` or `uv run qa batch` without activating the environment: its runs use the same `qa`. `compute_time` shows as *Run time*, and `qa batch` no longer warns that the server can't send emails unless you set `QA_NOTIFY`.
- Pipe `qa` without color codes: colors only on terminals and in CI logs (also where runners set `TERM=dumb`), never with `NO_COLOR`, always with `FORCE_COLOR`. What scripts read on stdout doesn't change. `--help` has examples.
- Create a project before its first results with **New project** (home page, Explore) or `qa project create`: you're its owner. When you can't, it says whom to ask or which namespace to use, and so do `qa init` and the first `qa run`. Owners archive projects from their **Access** tab ([create a project](/docs/user-guide/project-access#create-a-project), [from the shell](/docs/project-init#the-project-on-the-server)).

## Server and administration
### Upgrading
- The server image runs Python 3.14. If you installed compiled packages for its Python yourself, e.g. for the projects' code that batches started from the web app run in the server's container, install them again for Python 3.14.
- The upgrade adds an index of the runs that weren't deleted, so that **Delete old results** finds what's left to delete fast. It's built while the server keeps working. Scripts reading a commit's `deleted` from the HTTP API should read `artifacts_deleted`: `deleted` stays, deprecated ([deleting old data](/docs/storage/deleting-old-data)).

### Access and audit
- Projects get namespaces (the first part of their ids) and owners: whoever creates a new project owns it. Who creates them is `projects.create` and `namespaces.create`: nothing changes until you set them, and new servers' setup page offers stricter defaults ([who creates projects](/docs/backend-admin/project-access#who-creates-projects)).
- Find who ran, deleted or changed what in **Admin → Audit**: it now records batches started from the web app, redone and deleted runs, edited results, milestones, CI jobs started from the web app and retention cleanups, with their details. Filter by category and dates, export to CSV or JSON Lines, and send events to your SIEM with `QABOARD_AUDIT_STDOUT=1` ([the audit log](/docs/backend-admin/audit-log)).

### Deploying and operating
- `deployments/example.yml` is now `deployments/example/`, a whole site: keep your overlay, env files, nginx config, site package and site docs in their own repository, next to QA-Board's. `deploy.py` and the images find them there, and sites in `deployments/` keep working ([site directory](/docs/backend-admin/site-directory)).
- Follow each API request in the backend's logs: one line with its status, duration, user, project and a request id that its other lines carry. `QABOARD_LOG_FORMAT=json` for log collectors, `QABOARD_LOG_LEVEL` for the level. They replace uWSGI's request lines (`UWSGI_REQUEST_LOGS=1` brings them back). nginx's access log has the same ids. Neither has query strings, where tokens can be ([logs](/docs/backend-admin/logs)).
- Monitor the server with Prometheus: `QABOARD_METRICS=1` (Helm: `metrics.enabled`) serves request rates, errors and latency per endpoint, runs, jobs, storage and capacity at `/metrics` on the backend's own port, never through the proxy. The Helm chart adds a ServiceMonitor, alerts and a Grafana dashboard, and Compose gets an example Prometheus ([Prometheus metrics](/docs/backend-admin/monitoring#prometheus-metrics)).
- Let your users' chat clients, such as a self-hosted Open WebUI, use QA-Board's MCP tools at `<your QA-Board>/mcp`: turn on the optional `mcp` service, then register the client in **Admin → Connected apps**. Each user allows it once, with OAuth, and it only reads what they can ([connect MCP clients](/docs/backend-admin/mcp-clients)).

## Fixes
- **Delete old results** now deletes the runs of commits whose artifacts were deleted, and of commits whose branch QA-Board doesn't know. It reads git only for projects that list `project.milestones`, and an error in one project no longer stops the others ([deleting old data](/docs/storage/deleting-old-data)).
- A `project.milestones` with one reference (`milestones: v1.0`) protects it again, and one with no value no longer stops **Delete old results**. Deleting one run of a milestone keeps it, like deleting its batch: delete its files, or the milestone first.
