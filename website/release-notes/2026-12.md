## Web app

### Exports
- See every file's name before you export: **Export** previews each name, colored by what each part says (input, settings, file, new or reference), and won't export until no two files get the same name, with one-click fixes ([export files](/docs/user-guide/sharing#exporting-files)).
- Get short, readable names instead of hashes: names say only what tells files apart, usually the input (`night_street.png`), then the settings that differ and the side, e.g. `night_street__v1.2.png`. Pick the settings names say, name each side, or export only the new results or only the reference ([choose how files are named](/docs/user-guide/sharing#export-names)).
- Lay files out your way: in one folder, in new and reference folders for a diff tool, like the inputs, or with your own template, as links or copies. Folders the pattern matches come with their files, names open on Windows by default ([names Windows can open](/docs/user-guide/sharing#windows-names)), and presets save it all ([presets](/docs/user-guide/sharing#export-presets)).
- Export crops of the regions of interest, with or without the whole images: the image viewer's regions, the inputs' presets, your site's annotations, or where images differ from their reference. References are cropped at the same place ([export crops](/docs/user-guide/sharing#export-crops)).
- Find your exports in **Storage usage → Exports**, also those made before, each in its own folder with a `0.export.csv` listing every file's run, input and settings ([exports](/docs/user-guide/storage-usage#exports)). **Export (legacy)** stays unchanged for your scripts until the new export does what you need: tell us with **Tell us**.

### Reference runs
- Compare runs on different inputs without ids, like a register sweep's captures: the **Reference runs** row suggests the change of name that pairs them, e.g. `reg0x1A=05 → 03`, applied in one click and kept in the page's link ([pair by name](/docs/user-guide/reference-runs#pair-by-name)).
- Pick another reference run from the tag next to a run's name, or turn your pick into a rule for every run, like preferring reference shots with `unit = 2`. Runs are tagged only when there's something to know: another input, a tie, no reference ([pick another](/docs/user-guide/reference-runs#pick-another)).

### Benchmarks and flame graphs
- See a run's benchmarks next to the reference's: each one's time, its change, and whether it's beyond the noise the harness measured. Reads pytest-benchmark, Google Benchmark, hyperfine, Criterion, JMH and `go test` results ([benchmarks](/docs/user-guide/other-viewers#benchmarks)).
- Find what got slower in a flame graph: a table of the top functions and their change against the reference, comparisons that hold when profiles have different sample counts, search with regular expressions, icicle or flame layouts, and keyboard navigation ([flame graphs](/docs/user-guide/other-viewers#flame-graphs)).

### Run cards
- See when a run was done again: its card is tagged **attempt 2**, **attempt 3**..., with when the earlier attempts ran, who ran them and how they ended; their logs are in **Logs** ([run cards](/docs/user-guide/commit-page#run-cards)).

### Results in scripts
- Work on the runs you see from a script: **Script**, next to **Export**, shows a Python snippet or shell command for the runs shown ([use the runs in a script](/docs/user-guide/sharing#runs-in-scripts)). Metrics a script added after the run get a pencil mark that says who added them, when and with which script ([added metrics](/docs/user-guide/metrics#added-metrics)).

### Project admin
- Set quality gate rules no commit can change, as a project's owner, in the project's **Admin → Quality gate**: for every run or some batches or labels, and whether a commit that loosens its own rules fails. **Access** moved under **Admin** ([set a project's gate rules](/docs/user-guide/project-gate)).

### Your account
- See people's pictures next to their names, from your company's sign-in, and your job title and department in **Settings → Profile**. Change your QA-Board password in **Settings → Sign-in methods** ([your account](/docs/user-guide/account)).

## CLI and project setup

### Runners
- Run batches on Kubernetes with the `kubernetes` runner: each run is a pod of a Job, as your own user, with your shared storage, within your cluster's queues and quotas, and `runs_per_pod` keeps GPU pods busy with short runs. When pods wait, `qa batch` says why ([Kubernetes](/docs/kubernetes-runner)).
- Start Dask workers on Slurm, PBS, SGE, HTCondor, OAR, Moab or Kubernetes, not only LSF, with `runners.dask.cluster.type`, and stop waiting for workers that never start with `worker_start_timeout` ([other schedulers](/docs/dask-integration#other-schedulers)).
- Stop Celery batches with Ctrl+C, runs included. Runs start from the worker's environment, so they get what only workers know, like `CUDA_VISIBLE_DEVICES`, and more secret-looking variables stay out of them: list those they need in `runners.celery.forward_secrets` ([secrets](/docs/celery-integration#secrets)).
- Check everything a batch needs with `qa doctor`: *qaboard.yaml*, the server, the storage and the runner's permissions, with how to fix each problem. `--test-job` also starts a small job ([qa doctor](/docs/doctor)).

### Results in scripts
- Get the runs a web app page shows with `qaboard.runs(url)`, or by project, commit, batch and filter, as `Run` objects with their metrics and files; `qa runs <url>` prints their folders. `import qaboard` now works in any script: it no longer reads *qaboard.yaml* or git ([runs in scripts](/docs/apis#runs-in-scripts)).
- Add metrics and files to runs after they ran: `run.log_metrics({"sharpness": 0.4})` records who added each metric and with which script, and `run.log_artifact()` adds a file to the run's folder, with a token with the `ingest` scope ([add metrics](/docs/apis#log)).
- Read results from any language: the server describes its HTTP API at `/api/v1/openapi.json` for client generators and agents, and `/api/v1/docs` lists the endpoints and tries requests ([HTTP API](/docs/http-api)).

### Quality gate
- Get the gate's verdict on the pull request: `qa gate --post-comment github` (or `gitlab`) posts one comment, updated on each push and shared by every gate job. It says when runs only passed after being done again, and when the commit loosens its rules ([the gate on pull requests](/docs/quality-gate-pull-requests)).
- Write gate rules for one `qa batch` or one label, and list in `expect_batches` the batches the gate waits for. `gate.batches` is now `gate.labels` and `--batch` is `--label`, the old names still work. The rules project owners set in the web app are checked too ([scopes](/docs/quality-gate#scopes)).

### Benchmarks and flame graphs
- Bring benchmarks and profiles in with your tools' own files: list the harness's file in `outputs.visualizations` and `benchmark_metrics(path)` makes each benchmark a metric ([benchmarks](/docs/benchmarks)). Folded stacks, speedscope and *.cpuprofile* files show as they are, and `save_flame_graph()` converts `perf script` and pprof ([flame graphs](/docs/flame-graphs)).

### Runs that are done again
- Shared and CI runs done again get a new folder, `<run>_attempt2`..., and the first folder's *latest_attempt.txt* names the latest. `qa` and `qaboard.runs()` find it; scripts that build paths themselves must read that file, or keep reruns in place with `outputs: {reruns: in-place}` ([reruns](/docs/storage/where-is-the-data#reruns)).

### CI without stored secrets
- Send results from GitHub Actions or GitLab CI without storing a token: click **Trust CI jobs** in a service account's **Tokens** and copy the configuration it shows. `qa` exchanges the job's ID token for a short-lived token by itself ([upload from CI without a secret](/docs/ci-integration#ci-without-secrets)).

## Server and administration

### Runners
- Let users start, redo and stop batches on Kubernetes from the web app, as themselves, with the Helm chart's `runners.kubernetes` ([Kubernetes](/docs/backend-admin/kubernetes#start-batches-from-the-web-app)). Give each team its own namespace: users who start batches in one can act as each other there. **Stop runs** now also stops Dask, Celery and the server's own batches ([stop runs](/docs/backend-admin/runners#stop)).
- Keep the server's secrets out of the `qa batch` it runs for users with `local` or `celery`. Projects' code still runs in the server's container: use `lsf` or `kubernetes` when you don't trust every developer with it ([security](/docs/backend-admin/runners#security)).

### Settings and secrets
- Change most settings in **Admin → Settings**, without a deploy: git hosts, Jenkins, email, the web app's links... Each says what it does and where its value comes from, and **Save it here** moves a variable out of the environment, JSON ones too ([settings](/docs/backend-admin/settings), [move a setting](/docs/backend-admin/settings#move-a-setting-from-the-environment-to-the-database)).
- Secrets are encrypted in the database and never sent back to the browser. The key comes from `QABOARD_ENCRYPTION_KEY`, or the server generates one: back it up from **Admin → Settings → Security**. `qaboard-admin settings` and `qaboard-admin encryption` manage both from the shell ([the encryption key](/docs/backend-admin/settings#secrets-and-the-encryption-key), [from the command line](/docs/backend-admin/settings#from-the-command-line)).

### Accounts and sign-in
- Set up a new server from the web app: **Set up QA-Board** creates the first admin with the setup token from the backend's logs ([the first admin](/docs/backend-admin/user-management#the-first-admin)). Create local accounts and reset passwords in **Admin → Users** ([local accounts](/docs/backend-admin/user-management#local-accounts)).
- Keep profiles up to date from sign-in: name, email, job title, department and picture, also from Microsoft Graph for Entra ID ([pictures and profiles](/docs/backend-admin/sign-in#pictures-and-profiles)). Order the sign-in methods in **Admin → Sign-in**: it replaces OIDC providers' *Position* ([several providers](/docs/backend-admin/sign-in#several-providers)).
- Tokens CI jobs exchange last 6 hours (`tokens.ci_lifetime_minutes`), and the server must reach the CI's issuer. Projects' owners can trust GitHub, GitLab.com and your git hosts; other issuers need an admin ([service accounts](/docs/backend-admin/user-management#service-accounts)).

### Scripts and exports
- Tell scripts what to install besides `qaboard`, e.g. your site's package, in `web.cli_requirements` ([server settings](/docs/deploy#optional-environment-variables)). The API's description and reference page are public, also when sign-in is required, and work without internet access.
- Let scripts start Jenkins jobs without a token while they move to tokens, with `jenkins.anonymous_jobs` ([Jenkins jobs](/docs/backend-admin/user-management#jenkins-jobs-started-without-a-token)).
- Exports go to a new folder each time, in `storage.exports_root` or next to the commit's results, and storage scans track the exports they find. Scripts' `/api/v1/export` still works, deprecated: its answers have a `Deprecation` header to find its callers ([exports](/docs/backend-admin/storage#exports)).

## Fixes
- `qa gate` no longer waits, undecidable, for the reference's tuning iterations: they aren't runs it checks.
- Batches the web app starts with `QABOARD_TUNING_RUNNER=local` or `celery`, and runs redone without an LSF bridge, are no longer killed after 5 minutes ([on the server itself](/docs/backend-admin/runners#local)). The web app says where their `qa batch` runs, and shows stopped ones as **Stopped**.
- Export copies files with your groups: copies of files you read through a group failed. It now checks before copying that you can write the folder and read the files ([export files](/docs/user-guide/sharing#exporting-files)); admins set `QABOARD_GROUPS_COMMAND` ([users' accounts](/docs/backend-admin/user-management#users-accounts)). **Export (legacy)** exports real folders, not links Windows can't open.
