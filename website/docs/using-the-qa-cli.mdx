`qa` wraps your code: it runs it on inputs, saves the results and tells QA-Board about them.

## How commands look
Global options go **before** the command, the command's options after it:

```bash
qa [GLOBAL OPTIONS] COMMAND [OPTIONS] [ARGUMENTS]
qa --share --label my-test batch my-batch --runner local
```

Global options describe *what* you run: the configurations, the label, the platform, tuning parameters... They are the same for all commands. Run `qa --help` to list them, and `qa COMMAND --help` for each command's options, with examples.

| Command | What it does |
|---|---|
| `qa run --input PATH` | Runs your code on one input, then computes its metrics. |
| `qa batch BATCH...` | Runs on all the inputs of [batches](batches-running-on-multiple-inputs), locally or on a cluster. |
| `qa postprocess --input PATH` | Only runs your `postprocess()` function, on existing results. |
| `qa sync --input PATH` | Sends to QA-Board the metrics of a run, from its *metrics.json*. |
| `qa wait --output-id ID` | Waits for a pending run, used by `qa batch`. |
| `qa check-bit-accuracy` | Checks that outputs are the same as a reference commit's. See [bit-accuracy](bit-accuracy). |
| `qa check-bit-accuracy-manifest` | Checks that outputs are the same as the manifests saved next to the inputs. |
| `qa optimize` | [Optimizes parameters](auto-optimization): each evaluation is a `qa batch`. |
| `qa get [VARIABLE]` | Prints the project's variables: commit, storage locations, output directory of a run... |
| `qa init` | Starts a QA-Board project: creates *qaboard.yaml* and a sample entrypoint. See [project init](project-init). |
| `qa save-artifacts` | Saves the commit's [artifacts](storage/artifacts) (binaries, configs...). |

## Giving arguments to your code
Arguments that `qa` doesn't know are given to your code, as `context.forwarded_args`. To be explicit, or if they look like `qa`'s own options, put them after `--`:

```bash
qa run --input image.jpg --my-flag
qa run --input image.jpg -- --keep-previous   # --keep-previous is for your code, not for qa
qa batch my-batch -- --my-flag value          # with qa batch, use -- (other arguments are batch names)
```

## Environment variables
Every option can also be set with an environment variable: `QA_<OPTION>` for global options, `QA_<COMMAND>_<OPTION>` for a command's options. Each option's variable is shown in `--help`. The command line always wins.

```bash
export QA_SHARE=true           # qa --share
export QA_LABEL=my-experiment  # qa --label my-experiment
export QA_BATCH_RUNNER=local   # qa batch --runner local
export QA_RUN_KEEP_PREVIOUS=1  # qa run --keep-previous
```

A few more variables change how `qa` behaves:
- `qa batch`: see [batches](batches-running-on-multiple-inputs) (`QA_BATCH_CONCURRENCY`, `QA_BATCH_FAIL_IF_EMPTY`...).
- `NO_COLOR=1` disables colors (see [no-color.org](https://no-color.org)). By default `qa` keeps colors even when its output is redirected: QA-Board shows logs with colors.
- `QA_NO_CHECK_FOR_UPDATES=1` doesn't check daily for new versions of `qa`.
- `QA_NO_STREAM_REDIRECT=1`: `qa run` doesn't copy its output to *log.txt*. Useful with debuggers.
- `QA_USER` overrides your user name, `QA_STORAGE` where results are stored.
- `QABOARD_HOST`, `QABOARD_URL`... how to reach the QA-Board server, see [below](#connecting-to-a-custom-qa-board-instance).

## Flags worth knowing
### `qa --share`
When you run `qa batch` or `qa run` on your terminal, results are saved locally under **output/**, and *they are not visible in QA-Board*. To make them visible:

```bash
qa --share batch my-batch
```

:::tip
To make `--share` the default, set it in your shell's config: `export QA_SHARE=true`, or `alias qa="qa --share"`.
:::

In CI, results are always shared.

### `qa --dryrun`
`qa` commmands support a `--dryrun` mode, where they print actions they would take, but don't actually do anything. In particular it helps see quickly what inputs you defined in a batch:

```bash
qa --dryrun batch my-batch
# qa run --input image/A.jpg
# qa run --input image/B.jpg
```

:::note
For `qa --dryrun run`, you are expected to handle `if context.dryrun: ...` yourself in `run()`. The use-case is usually printing how you would call an executable, for debugging.
:::

### `qa --label my-label`
Everytime you `qa run`, it erases previous results. So if you want compare different versions by tweaking doing `qa run`, it won't work. Fortunately, `qa` lets you give a "label", or "experiment name" to runs. Results with different labels are stored separately:

```
qa --label without-optimizations batch validation-images
qa --label    with-optimizations batch validation-images
```

:::tip
To keep previous output files, use `qa run --keep-previous` (or `export QABOARD_RUN_KEEP=true`). It can be useful if you are debugging long runs and implemented a caching mecanism. *(Experimental)*
:::

### `qa --offline`
Doesn't tell QA-Board about runs. Useful if... you don't have a server, or when experimenting.

## `qa batch`
### Batch Runners
While `qa run` uses the local environment, `qa batch` will offload computation to a "runner" backend.

Available runners:
- `local`: [local multiprocessing](local-multiprocessing) with [`joblib`](http://joblib.readthedocs.io/). Default if no other runner is configured, and on Windows instead of `lsf`. Set the concurrency with `--local-concurrency`, `QA_BATCH_CONCURRENCY` or `runners.local.concurrency` in *qaboard.yaml*.
- `lsf`: 1 [LSF](lsf-integration) job per run. Limit how many run at the same time with `--lsf-concurrency` or `runners.lsf.concurrency`.
- `dask`: a pool of long-lived [Dask workers](dask-integration), started as LSF jobs. Best for many short runs. Set the concurrency with `--dask-concurrency` or `runners.dask.concurrency`.
- `celery`: [Celery](celery-integration) workers.
- `windows`: runs sent to Windows hosts via [Jenkins](jenkins-integration).

Choose the runner with `--runner=local`, and set a default with `runners.default: local` in *qaboard.yaml*. Without `runners.default`, `qa batch` uses the first runner configured under `runners` (other than `local`), else `local`.

### Dealing with existing results
When you try to re-run already existing results, The behaviour of `qa batch` can be changed with the `--action-on-existing` flag:
- `--action-on-existing=run`: overwrite the old results (default).
- `postprocess`: only call the `postprocess()` function, not `run()+postprocess()` as usual. (Note: it's also provided by `qa postprocess`)
- `sync`: update the output file manifest and read metrics from *$output_dir/metrics.json*. (Note: it's also provided by `qa sync`)
- `skip`: do nothing
- `assert-exists`: run nothing, and fail if some runs don't exist, in QA-Board or with results in their output directory. It lists the missing runs. Useful e.g. before comparing results.

The default can be set in *qaboard.yaml* with `outputs.action_on_existing`.

Similarly, `--action-on-pending` (or `outputs.action_on_pending`) decides what to do when the same runs are already pending: `wait` (default: wait for them, and run again those that failed), `sync` (use those runs' results), `skip` or `run` (run as usual, can cause races).

### Exploring tuning parameters
`--tuning-search` runs each input with every combination of parameters (`--tuning-search-file` reads them from a YAML or JSON file):

```bash
qa batch my-batch --tuning-search '{"parameter_search": {"gain": [1, 2], "mode": ["fast", "accurate"]}}'
# 4 runs per input
```

Use `"search_type": "sampler"` and `"search_options": {"n_iter": 10}` to sample 10 random combinations instead. In your code, the parameters are in `context.params`. It's what QA-Board uses to [tune from the web app](tuning-from-the-webapp).

## `qa get`
Prints variables about the project and the commit. Without a variable, it prints the main ones, as JSON:

```bash
qa get                                    # JSON: project, commit_id, outputs_commit, batch_dir...
qa get commit_id
qa get outputs_commit                     # where results are stored for this commit
qa --label my-test get batch_dir
qa get output_dir --input images/a.jpg    # with --input: the variables of the run
qa get configurations --json
qa get config                             # the full configuration, after merging qaboard.yaml files
```

## Shell completion
To complete commands and options with <kbd>Tab</kbd>:

```bash
qa --install-completion   # bash, zsh, fish or powershell, then open a new shell
```

## Exit codes
`qa` exits with `0` on success, `1` when runs fail (`qa run`, `qa postprocess`, `qa batch`, bit-accuracy checks...) and `2` when the command line is invalid, e.g. a missing `--input` or an unknown `--runner` value (options that `qa run` and `qa batch` don't know are given to your code). `qa run`, `qa postprocess` and `qa sync` print the run's metrics as JSON, on the last line of their output. See also [using qa from scripts, CI and AI agents](apis#using-qa-from-scripts-ci-and-ai-agents).

## Connecting to a custom QA-Board instance
Use `qa --offline` to ensure you don't connect to a QA-Board instance. It's useful if... you don't have one (?).
The default connection settings can be overriden by environment variables. For example:

```bash
export QABOARD_PROTOCOL=http
export QABOARD_HOST=my-server:5151
# or: export QABOARD_URL=http://my-server:5151
```

See [Client Installation](installation#connecting-to-a-custom-qa-board-server).
