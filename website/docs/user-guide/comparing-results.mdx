QA-Board shows your results next to a **reference**: the results you compare them with. This page helps you choose
that reference, and read what each run is compared with.

A number alone says little: is a PSNR of 29.6 dB good? Next to the reference's, it says what your change did: +5%.
The header of a commit page says what you compare: a row for the **new** results you look at, then a row for each
**reference** they're compared with: a commit, one of its batches, maybe with a filter. Each run is shown against the
reference's run of the same input.

<Shot
  id="commit/named-comparison"
  caption="The camera ISP's bilateral denoiser, in the first row and in blue, against the release before it, isp-4.1, in purple: each image says which one it is. Here the new results were named “bilateral” (see Name what you compare)."
/>

Each row has the same columns: the name, the short commit id (click it to copy the full id), what the results are,
the batch with how its runs did, the filter, and actions. For a reference, the row first says why it's there:

| The row says | The reference is |
|---|---|
| **Latest on main** | The latest commit of the project's reference branch: the [default reference](#the-default-reference). |
| **Older on main** | An older commit of the reference branch. |
| **Earlier on this branch** / **Later on this branch** | Another commit of the new commit's branch, before or after it. |
| ★ and its notes | A [milestone](#milestones): its notes (else its commit's message), and what tells it apart from the other milestones you compare: its group, who saved it and when. |
| **Same commit as new** | The same commit, with another batch or filter. |

Then comes the commit's message, who made it and when. ⓘ gives the rest: the full commit id (type another one there),
the branch, the date.

## The default reference {#the-default-reference}
When you open a commit, the reference is the **latest commit with results on the project's reference branch**, often
`main` (the project sets it in *qaboard.yaml*): what your change does to the code everyone uses. Its row says
**Latest on main** and it's called **main**. The page's link saves that commit, so a link you share today compares
with the same commit next week: once `main` moves on, the row says **Older on main**.

## Choose another reference {#picking-a-reference}
To compare with a release, another branch or a colleague's commit, change the reference's row. The **new** row works the
same way.

- Click **⇅**, at the start of the new results' row, to swap new and the reference.
- Click the **✎** (Change) of a row: pick the reference branch's latest commit, a [milestone](#milestones), or
  another project.
- Click **ⓘ** to type a commit hash (short hashes work), or click the branch name to select that branch's latest
  commit.

<Shot
  id="commit/change-menu"
  caption="The reference's Change menu: swap new and the reference, pick the reference branch (main), or a milestone, like the detector's releases."
/>

Each row also has its own batch selector and filter box: you can compare any
[batch](/docs/user-guide/finding-results#batches) of any commit with any other, or only some of their runs. With a
filter, the box says how many runs match, like **8 of 18**.

<details>
<summary>Every item of the Change menu</summary>

| Menu item | What it does |
|---|---|
| **Change project** | Pick results from another project, e.g. another sub-project of a monorepo, or a fork. |
| **Swap new and the reference** | Swaps the two rows' results, with their batches, filters and names. Same as **⇅**. |
| **Compare with these results** / **Show it as the new results too** | Copies this commit, batch and filter to the other row, instead of what it shows. |
| **Stack another reference…** | In the reference's row: compare with [several references](#several-references), one at a time or [together](#show-references-together). |
| **Remove from comparison** | Clears the commit. With several references, removes the one compared, with an **Undo**. |
| The reference branch | Selects its latest commit. |
| Milestones | Your favorites, your milestones, the project's, and those from *qaboard.yaml*. Their batch and filter are selected too. See [Milestones](/docs/user-guide/milestones#finding-milestones). |

</details>

### Compare two batches of the same commit {#compare-two-batches-of-the-same-commit}
A tuning experiment runs on the same commit as CI. To see what it changed, compare its batch with the commit's **CI**
batch:

1. In the **new** row's batch selector, pick the experiment, e.g. `tune-denoise`.
2. Click its **✎** (Change), then **Compare with these results**. The reference's row now shows the same commit and
   batch.
3. In the reference's batch selector, pick **CI**. Its row says **Same commit as new**, and it's called by its batch.

Each run of the experiment is now shown against the CI run of the same input.

## Compare with a milestone {#milestones}

A milestone keeps results worth comparing with, like a release or your best tuning so far. Save one with the star of
a row, then pick it in the reference's **Change** menu, or add it with **+**. Its row is named after it and shows its
notes: write in them what makes it worth comparing with. See [Milestones](/docs/user-guide/milestones).

## Name what you compare {#naming-what-you-compare}
Click a row's name to rename it, for example `ISP v2` and `ISP v1` (or press <kbd>F2</kbd> on the row). The whole
page then uses these names: the labels of images and videos, the legends of plots, the headers of text diffs and HTML
outputs, the flame graphs' choices, the **Summary**, and the columns of the **Metrics Table** and **Metrics Diff**
(`ISP v2 − ISP v1`). The names are saved in the link, so people you share it with see them too. Erase a name to go
back to the one QA-Board gives.

References you don't name are called by why they're there: **main** for the latest commit of the reference branch,
their milestone's name, their batch for the same commit as new (**nightly**), else their short commit id
(**a3f9c21**). Two references with the same name are told apart by their batch or filter. You can still rename a
milestone on the page: the milestone's name then shows next to its star.

<Anchor id="metric-diffs-and-colors" />
Each side also has its color, in its row, in the viewers' labels and in plots: **new** is blue, and each reference has
its own color (purple, magenta, teal, violet, then gray). Results keep their color wherever they go: when you swap
new and the reference, the colors swap too. Green and red never stand for a side: they say what got better or worse
(see [what the colors mean](/docs/user-guide/metrics#colors)).

## Compare with several references {#several-references}
To compare with the last release, a tuning experiment and the latest `main` on one page, add them. The new results
are compared with one reference at a time, and you switch between them. The image viewer
[shows them all together](#show-references-together).

1. Click **+**, at the end of the last reference's row.
2. Add a commit, a branch (its latest commit), a milestone, or a copy of the reference to change its batch or
   filter. It's compared with right away, and the reference you were looking at keeps its row.

<Shot
  id="commit/stack-reference"
  caption="Click + to compare with another commit, branch or milestone too: the reference you look at stays in the list."
/>

3. Switch references with the radio buttons at the start of their rows, or press <kbd>r</kbd> (next) and
   <kbd>Shift</kbd> <kbd>r</kbd> (previous). Each keeps its row, batch, filter and name: nothing moves.

<Shot
  id="commit/reference-rows"
  caption="Each reference has its row, which says why it's there. Click its radio button, or press r, to compare with it."
/>

The row of the reference compared is highlighted. The other rows show their batch with how its runs did, and their
filter: to change them, compare with that reference first. Past four references, the rows scroll: three and a half
show, the footer says how many are out of sight, and **Show all** lists up to twelve. While you scroll, the reference
compared stays at the top or bottom of the list.

The references are saved in the page's link: share it, and others can switch between the same references.

<details>
<summary>Reorder, rename and remove references</summary>

- Drag a row by its name to reorder it: a line shows where it goes, before or after the row under the mouse. Or
  press <kbd>Alt</kbd> <kbd>↑</kbd> <kbd>↓</kbd> on the row.
- Click a row's name, or press <kbd>F2</kbd> on the row, to rename it. Press <kbd>Delete</kbd> to remove it: a
  message offers to **Undo** it, and the browser's Back button works too.
- A row's **⋯** compares with it, swaps it with new, makes a copy (to change its batch or filter), renames, moves or
  removes it.
- Drag the new results' row on a reference's (or a reference on new) to swap them. It's the same comparison,
  reversed, and nothing is replaced. To stop comparing with what was new, swap, then remove it.
- A reference keeps its name and its color when you reorder or remove the others. The color of a reference you
  remove goes to the next one you add (or to the first gray one). A copy of a reference you named "night" is
  "night copy", in the next free color.
- When you swap new and a reference, the colors and the names you gave follow their results.
- When there isn't room, the rows' details give way first: the branch, then who and when, and the commit ids.
- Only the reference compared, and those [the image viewer shows](#show-references-together), are loaded with all
  their runs. Once the page is idle, the next and previous ones load in the background (unless they have thousands of
  runs).

</details>

### See several references together {#show-references-together}
The metrics, the plots and most viewers compare with one reference: the one whose radio button is checked. The image
viewer shows more: as soon as you compare with two references or more, it shows the new image and all of them, each
in its tile, zoomed together. Each is compared with new, the anchor, or with the reference you make the anchor. See
[Several references at once](/docs/user-guide/image-viewer#several-references-at-once).

- **Leave a reference out**: click the eye of its row. Each is shown at first.
- **One at a time**: in a row's **⋯**, **Show one reference at a time** goes back to one reference at a time in the
  image viewer, and **Show the references together** back. Your browser remembers it.
- **Compare with a reference**: click its radio button to compare with it and make it the anchor, or click its name
  on an image: the other images, new included, are then compared with it. Click new's name on an image to make new
  the anchor again. <kbd>r</kbd> and <kbd>Shift</kbd> <kbd>r</kbd> change only the reference compared: when a
  reference is the anchor, the anchor follows it.
- **Reorder the images**: the tiles follow the rows' order, new first. Drag the rows to reorder them. Selecting
  another reference or anchor moves nothing.

Comparing with another reference keeps as many references shown: it takes the place of the one it replaces. The
choice, the anchor and the hidden references are saved in the page's link.

<details>
<summary>Limits</summary>

- Only the image viewer shows several references together: the metrics and every other viewer compare with the
  reference whose radio button is checked.
- Each reference shown loads all its runs, which is slow for commits with thousands of runs, and adds images to each
  run's card: a handful of references is the practical maximum. Hide the others with their eye, or show one at a time.

</details>

## How runs are matched {#how-runs-are-matched}
Each new run is compared with one reference run: the most similar one. QA-Board looks for the same input first (or
the same [`metadata.id`](/docs/metadata-integration-external-databases#creating-metadata)), then
the closest configuration, the closest tuning parameters, and the same platform. The closest is the one with the
fewest different settings; between as many, the one whose values are the most similar: for `base-v1`, `base-v2`
rather than `other`, for `gain: 3`, `gain: 4` rather than `gain: 100`.

When the best match is not identical, an orange tag with a `≠` warns you on the run: **Config** or **Platform**
(in tables, **Input** too). Hover it to see what the reference run used. **Config** shows how the configurations and
tuning parameters differ, line by line, and says when other reference runs were as close.

Runs on other inputs, runs without a reference, and runs with several reference runs as close say so next to their
name: click it to pick another reference run, or pair runs by name, like a register sweep's captures. See
[Pick each run's reference run](/docs/user-guide/reference-runs).

<Shot
  id="commit/config-tag-diff"
  caption="The Config tag of the int8 release's run at 416 px: compared with the fp32 release's run at 320 px, the closest, it removes fp32, adds int8, and changes the size and the model."
/>

:::caution
If you filter the new runs, filter the reference the same way (**Filter the reference's runs…**). Runs are only
matched with the reference runs its filter leaves, and the **Summary** compares the new runs with every reference run
of the same inputs, whatever their configuration.
:::

## Read configurations {#reading-configurations}
A run's configuration is what it ran with: configuration files like `base` or `low-light`, values like
`isp.nr.strength: 2`, and tuning parameters. Run cards show each of these settings as a tag, compared with the
reference run's.

Take the detector's int8 release, kd-1.3, against the fp32 release, kd-1.2. Its run on `slices/small-objects` says:

<Shot
  id="commit/run-badges"
  caption="The int8 run against the fp32 release: fp32 removed, int8 added, size-320 the same, and the model a changed tuning parameter. The orange Config tag says the reference run had other settings."
/>

- `− fp32`, red and struck through: the reference run used `fp32`, this one doesn't.
- `+ int8`, green: this run added `int8`.
- `size-320`, gray: both runs have it.
- `model: "kd-1.2-fp32-320" → "kd-1.3-int8-320"`, orange, with a wrench: a tuning parameter whose value changed, the
  reference's value first.
- **≠ Config**, a filled orange tag: no reference run had the same settings, so this run is compared with the
  closest one (see [how runs are matched](#how-runs-are-matched)).

Each run is compared with its own reference run, and says how they differ. The release also ran its models at
416 px, which the fp32 release didn't: those runs are compared with its 320 px runs, and their tag
`size-320 → 416` marks only the part that changed. Above the runs, **vs. reference** sums up the changes, with how
many runs have each one.

<Shot
  id="commit/config-diff"
  caption="The int8 release's runs at 320 and 416 px against the fp32 release: each run shows what it added, removed and changed, and vs. reference sums it up above them."
/>

With many runs on the page, most settings are the same for all of them. To show you what matters, each run only shows
its **own** settings: what all the runs share hides behind a dashed tag like **··· 9 shared**. Hover it to see those
settings, click it to show them in this run. The top of the page lists them once, next to **All 12 runs**. Hover any
tag to see what it means and copy it.

- **What all the runs share** follows the filter: filter runs, and what the remaining ones share hides too. The
  **··· shared** tags sit where the settings they hide are when those come first or last
  (`··· 2 shared` `night.yaml` `··· 7 shared`), else in one tag, first.
- **Changes all runs have**, e.g. when the reference commit used other default settings, are listed once at the top of
  the page, next to **vs. reference**, with how many runs have each change. Runs don't repeat them: their
  **··· shared** tag lists them, and the **Config** tag's diff shows them.
- **Long strings that vary between runs** start with `…` when they share a long beginning, e.g. `…scenes/night.yaml`.
  Hover them for the full string.
- **Long settings**, like commands, paths or lists, are shortened with `…`. Hover one to read it, or **click it to
  show all the settings in full**, in every run, wrapped on several lines. Click one again to shorten them. The web app
  remembers your choice, also in **Settings → Preferences** and the **Configuration** section of the View options.
- **To always see full configurations**, turn off **Hide them in each run**, at the top of the page or in the
  **Configuration** section of the [View options](/docs/user-guide/commit-page#view-options). Runs then show all their
  settings, the shared ones outlined.

<details>
<summary>Every kind of tag, what counts as a setting, and copying settings</summary>

| Tag | Means |
|---|---|
| gray | The same as the reference run. |
| green, with **+** | Added: the reference run doesn't have it. |
| red, struck through, with **−** | Removed: only the reference run has it. |
| orange, `gain: 3 → 4` | Changed: the reference's value, then this run's. For strings, only the part that changed: `conf/[day → night].yaml`. |
| with a wrench | A tuning parameter (`qa --tuning`), shown after the configuration, in full, even when all runs share it. |
| dashed, **··· 9 shared** | Settings all the runs shown share, hidden in each run. |

- Each string of a configuration (`base`, `conf/night.yaml`) is a setting, and so is each value of its JSON objects
  (`isp.nr.strength: 2`).
- A list of values is one setting. Long ones show their first values and their size:
  `tone_lut: [0, 0.016, 0.032, …] 64 values`, `ccm: [[1.6, -0.4, -0.2], …] 3×3`.
- A list of objects has a setting per value (`layers[1].stride: 2`), so that you see which one changed.
- To copy settings, hover them: copy a setting as text or JSON, or the run's settings as `qa` options
  (`-c base -c '{"gain": 4}' --tuning '{"nr": 2}'`), as JSON, or as a tuning search space. The **Config** tag's diff
  copies the changes, or the reference's `qa` options.
- Short configurations (one or two short settings) are never hidden, and the **Logs** view always shows full
  configurations.

</details>
