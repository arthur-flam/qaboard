From a commit's page, you can run its code again without a terminal:

- [Redo runs](#redo-stop-and-clean-up-runs) that failed, were deleted or got stuck.
- [Run the commit on other tests or settings](#running-tests-and-tuning), like the int8 detector on the slices where it loses small objects.
- [Start a tuning experiment](#running-tests-and-tuning) and [see which values win](#tuning-analysis): try a grid of parameters, or let an optimizer search them. New to tuning? Start with [Tune parameters, step by step](/docs/user-guide/tuning).

:::info What you need
- **Sign in**, at the bottom of the sidebar. Signed out, the buttons that start runs are grayed out, next to a
  **Sign in** button. You also need the developer role on the project: see
  [Project access](/docs/user-guide/project-access).
- The commit's **artifacts**: the build and configuration files your CI saved. If they were deleted, QA-Board can bring them back first (see [If runs don't start](#if-runs-dont-start)).
- A **task runner** for your project, like a compute cluster, that your QA-Board server can start runs on. If there is none, the form says so: ask whoever integrated QA-Board in your project to [choose one](/docs/runners), and your QA-Board admins to [let the server use it](/docs/backend-admin/runners).
:::

## Run tests or a tuning experiment {#running-tests-and-tuning}
On the detector's `quant/int8` branch, the commit that calibrates int8 with percentiles still loses 7% of the AP on small objects. Can the post-processing win it back? Here is how to try 2 score thresholds and 2 NMS IoUs on `quant-search`, its outdoor and small-objects slices:

1. On the commit page, select **Run Tests / Tuning** in the sidebar, under **Tuning**.
2. In **Batch label**, name the new batch, e.g. `int8-nms`. Its runs stay apart from the CI's.
3. In **Batch of inputs+configurations**, type the batch of tests to run: `quant-search`. The form shows **2 tests** below it: hover it to see the inputs and their configurations. To find a batch, or write your own, see [Choosing the tests to run](/docs/user-guide/available-tests).
4. If the form lists **platforms** (like Linux and Android), pick the one to run on.
5. Under **Parameters**, keep **Choose the values**, and write each parameter with the values to try:
   ```json
   {
     "score_threshold": [0.2, 0.3],
     "nms_iou": [0.5, 0.7]
   }
   ```
   With **All combinations**, the form says it **Explores 4 combinations**. To run the tests with the commit's own settings, click the **no tuning** example instead.
6. Check the total, **8 total runs** (4 combinations on 2 tests), and click **Start 8 runs**.

<Shot
  id="tuning/manual-form"
  caption="Every combination of 2 score thresholds and 2 NMS IoUs on the 2 tests of quant-search: the form says 8 runs before you start them."
/>

A message confirms that `int8-nms` started, with **Show its logs**. Its runs show up in the new batch, and when the last one ends, QA-Board [emails you](#emails-when-batches-end) if your server sends emails. Next: [look at the results](#tuning-analysis).

QA-Board checks the form as you fill it: **Fix this to start** lists what would make the batch fail, like an unknown batch, and **Before you start** warns about the rest, like artifacts it must restore first. The form remembers what you entered, per project. If the batch doesn't start, the commit page says why: see [If runs don't start](#if-runs-dont-start).

:::tip Start from a run's settings
Hover a run's configuration tags and choose **Copy as a tuning search space**. Paste it in the editor under **Choose the values**, then add the values you want to try.
:::

<details>
<summary>Every option of the form</summary>

| Option | What it does |
|---|---|
| **Batch label** | The new batch's name: letters, digits and `_.@:=`, other characters become `-`. Reusing the label of an existing batch adds runs to it. |
| **Batch of inputs+configurations** | A batch, or several with a pattern like `batch-*`. Below it: how many tests, and the files that define the batch, e.g. *Defined in qa/batches.yaml*. Click a file to open it on your git server at this commit, or, for the shared and private batches, in **Available Tests** at the batch. When several files define a batch, the last one wins, and the form says which. |
| Platforms | Shown when the project has several. The runs use `qa --platform` with the one you pick. |
| **Choose the values** or **Search automatically** | List the values to try yourself, or let an [automated tuning](#automated-tuning) search ranges for the best metrics. With a grid of 12 combinations or more that a search would cover with fewer runs, the form offers **Search these ranges automatically**: it fills the search with your parameters, their ranges, and the values you fixed. |
| **Start from an example** | **no tuning**: the tests with the commit's settings. **simple-combinations**: a grid. **list-of-combinations**: a list of parameter sets, each its own grid, whose runs add up. **1x2 matrix**: a parameter whose value is a matrix. **function**: a JavaScript function that returns the parameters, for ranges and loops. |
| **All combinations** or **Sampling** | Every combination of the values (a grid), or a uniform sample of as many as you choose. |
| Pasting `key=value` lines | They become the JSON the editor expects: `block.threshold=10` becomes `"block.threshold": [10]`, and space-separated matrices like `[1 2 3]` become JSON arrays. |
| **Overwrite previous identical runs** | On, the default: runs that already exist in the batch, with the same input, configuration and parameters, run again. Off: they're kept, and only the missing runs start. |
| **Will run as** | With LSF, the user the runs start as, with their shell environment. It's you. |
| Limits | At most 5,000 runs per batch. Over 1,000, the form asks you to check that the cluster has room. |

</details>

### Let the optimizer search the parameters {#automated-tuning}
When a grid would be too big, or when you'd rather say what to improve than guess values, choose **Search automatically**
under **Parameters**. It sets up a search in three steps: the
**Parameters to tune** and their ranges, **What “better” means** with the metrics your runs return, and the
**Budget**, the number of evaluations. Click **Start automated tuning**: each evaluation runs the batch, first with
random parameters, then with parameters picked from the results of the previous ones. To choose the parameters and
the budget, and read what the search found, see [Find the best parameters automatically](/docs/user-guide/automated-tuning).

For the detector, `tune-int8` searched the calibration percentile, the layers to keep in fp32, the score threshold and the NMS IoU on `quant-search`, for the best AP on small objects and mAP with a small model. There is no email when an automated tuning ends yet. See [Automated tuning with qa optimize](/docs/auto-optimization) for every setting.

## Look at the results {#tuning-analysis}
1. In the **new** bar's batch selector, pick the new batch, `int8-nms`. Its runs show up as they start, and the page refreshes by itself while some are pending.
2. A blue message above the results says the batch tried 4 parameter sets: click **See which is best**. Or select **Tuning Analysis** in the sidebar, under **Tuning**: it's highlighted when the batch has parameters to compare.

<Clip
  id="tuning/launch-to-analysis"
  caption="The form starts 8 runs. Once they're done, pick their batch: Tuning Analysis draws one line per combination of score threshold and NMS IoU."
/>

Tuning Analysis compares the batch's **parameter sets**: the runs that share the same values of the parameters that change. It combines each set's metric over its tests, their average or their median, and reads from top to bottom:

1. **Compare parameter sets by**: the metric that decides. When the project doesn't say whether higher or lower is better, the page asks.
2. The **best** value, how far it is from your defaults or from the worst set, and on how many tests the best set wins.
3. **What this tells you**: what to check and what to do next, in plain words. For instance that the best value is the highest you tried, so better ones may be above it, or that the best set on average loses on most tests.
4. **Best parameters**, with the values tried and each parameter's **Impact**: how much it changes the metric.
5. **Every parameter set at a glance**: one line per set across its metrics and parameters. Follow the best-colored lines to see which values they share, hover a line to read it, and drag along an axis to keep a range.
6. **How each parameter affects** the metric, **Trade-offs with another metric**, and **Test by test**, which shows where the best set loses.
7. **All parameter sets**, each with **Outputs**, to look at its runs, and **Run…**, to run it on other tests.

The **?** buttons explain each idea, like an impact or a best trade-off, with links to learn more.

From there, **Run the best parameters…** opens the form with them, to check them on a larger batch, and **Search automatically…** sets up an [automated tuning](#automated-tuning) over the ranges this batch tried.

For the inference gateway, a sweep tried the batching settings of the sharded cache: max batch 1, 16 and 64, by max delay 0, 250, 1000 and 4000 µs, on the steady-high and heavy-tail-high load profiles. Comparing by **CPU per request**, with p99 as the other metric, **Trade-offs with another metric** shows which settings are worth it:

<Shot
  id="tuning/frontier"
  caption="Each configuration's CPU per request against its p99: the defaults picked, max batch 16 and 250 µs of delay, are on the frontier."
/>

For an automated tuning, the report is about the search: its progress, what it found, which parameters matter, and what to do next. See [Read the results](/docs/user-guide/automated-tuning#results).

### No metrics yet? Score the runs with a script {#score-runs}
Tuning Analysis needs a metric: a number that scores each run. If your runs return none, or not the one you care about, you don't have to run again. The page gives a short Python script that goes over the batch's runs: write the function that computes your number from a run's files, run the script, and each run gets the metric. Then reload the page. See [Add metrics to runs](/docs/apis#log).

On a batch whose runs all use the same parameters, the view says how to start instead: score the runs, try other parameters, and read the results. It also lists the commit's other batches that have parameters to compare.

<details>
<summary>Every part of Tuning Analysis</summary>

| Part | What it shows |
|---|---|
| Automated tuning report | For an automated tuning: see [Read the results](/docs/user-guide/automated-tuning#results). |
| Parameter sets | The runs are grouped by the values of the parameters that change in the batch, from their configurations and tuning parameters. Runs that set none of them are **the defaults**. A test is an input with its other settings. |
| **Compare parameter sets by** | Any metric that changes between the sets, the tables' metrics first. **Average** or **Median** combines each set's tests. |
| Sets that miss tests | A set with results on fewer tests than the others isn't ranked: its average wouldn't be comparable. The table marks it. |
| **Impact** | How much of the metric's variation between the sets a parameter explains on its own. It needs 2 parameters or more, and is a hint: with few sets it is noisy. |
| **Every parameter set at a glance** | Parallel coordinates: an axis per metric and per parameter, a line per set, colored by the metric compared. Lines that share a value are spread around it, so you can follow them. Drag along an axis to filter, click a category to keep it; the table follows. From an axis's menu: color by it, flip it, use a log scale, hide it. Drag a title to reorder. |
| **How each parameter affects** | A dot per set, and the average at each value. The star is the best set. |
| **Trade-offs with another metric** | The metric compared against another one. The highlighted sets are the best trade-offs, the Pareto front: nothing else is better on both. |
| **Test by test** | The 8 best sets on each test. A cell is darker the further it is from that test's best, and the tests where the best set loses the most come first. |
| **All parameter sets** | Every set with its metrics and parameters. **Outputs** filters the page to its runs; **Run…** opens the form with its parameters. |

- The view uses the runs that match the filter, and leaves out failed and pending runs.
- The metric, the aggregation and which way is better are in the link: share it, and others see the same page.

</details>

### Compare with the CI batch {#compare-with-the-ci-batch}
To see what the experiment changed against the commit's CI runs, show `int8-nms` in the new bar and the same commit's
**CI** batch in the reference bar: see
[compare two batches of the same commit](/docs/user-guide/comparing-results#compare-two-batches-of-the-same-commit).
To look at one combination, filter the new bar's runs, e.g. `nms_iou:0.7 score_threshold:0.3`: the Summary otherwise
aggregates all of them.

## Redo, stop and clean up runs {#redo-stop-and-clean-up-runs}

| To... | Where |
|---|---|
| Redo **one run** | On its card (Visualizations or Output Files views), ☰ menu → **Redo**. In the Logs view, its **⋯** menu |
| Redo the **failed** runs of a batch | Commit bar menu (☰) → **Redo failed runs** |
| Redo **deleted** runs | Commit bar menu → **Redo deleted runs**, or the button in the "N of the runs below were deleted" message |
| Redo **all** runs of a batch | Commit bar menu → **Redo all runs…** |
| **Stop** pending runs | The **Stop runs** button above the views, shown while runs are pending |
| Unblock a run stuck as pending | On its card, ☰ menu → **Mark as failed**, then **Redo** it |
| Delete runs, or only their files | Card ☰ menu (**Delete…**, **Delete output files…**), or the commit bar menu: failed runs, the whole batch, several batches |

<Shot
  id="commit/run-menu"
  caption="A run card's menu: redo it, delete it, or delete only its output files. While a run is pending or running, Mark as failed replaces Redo."
/>

Redone runs use the commit's saved artifacts and the same input, configuration and parameters. They also use the runner they were started with, and the batch's runner settings, like how many runs can run at the same time: QA-Board starts them together, with a single `qa batch`. Follow them with the counters under the filter box, or in the [Logs](/docs/user-guide/logs#batch-commands) view, under **Started from QA-Board**.

:::danger
Deleting runs can't be undone: their output files and metrics are gone. QA-Board asks you to confirm, and won't delete batches or commits saved as [milestones](/docs/user-guide/milestones).
:::

<details>
<summary>Filters, stuck runs and other details</summary>

- When you filter the batch's runs, the commit bar menu only redoes the runs that match: **Redo the N runs that match the filter…**, **Redo filtered failed runs**, **Redo filtered deleted runs**. Moving runs follows the filter too: **Move the filtered runs to another batch**. Deleting doesn't: it applies to the whole batch, and the confirmation says so.
- **Redo all runs…** asks you to confirm: the runs' current results are replaced when they start.
- **Mark as failed** is for runs stuck as pending or running whose job is gone, e.g. killed by the cluster: they would never report.
- **Delete files, keep metadata**, in the commit bar menu, makes its delete actions free storage only: the runs and their metrics stay. A box then limits it to files matching patterns like `*.png`.
- A batch with pending runs can't be renamed.

</details>

## Get an email when a batch ends {#emails-when-batches-end}
Runs can take hours, or wait for a busy cluster. When you start a batch from the form, QA-Board emails you once, when its last run ends: how many runs failed, the main metrics against their targets, the best combinations when you tuned parameters, and links to the failed runs' logs. Under the **Start** button, the form says when it will email you.

<details>
<summary>What the email says, and when you get one</summary>

The email says:
- whether all runs succeeded, how many failed, and how long the batch took,
- the median of the project's main metrics over the successful runs, and whether they meet their targets,
- when you tuned parameters, the best combinations on the first main metric,
- which runs failed, with links to their logs,
- the commit, the batch and the inputs, with links to them in QA-Board.

Good to know:
- You get **one email per batch**, when no run is left pending: not when the first run fails. If you stop the batch from QA-Board, there is no email.
- For **pipelines**, whose steps start other batches, you get one email when the whole pipeline is done, not one per step.
- QA-Board emails the address of your account, or the one your administrators configured for your username. The confirmation message after you start says where.
- Your QA-Board server must be configured to send emails. There is no email for automated tuning yet.
- Batches you start from a terminal with `qa --share batch` email you too: see [`QA_NOTIFY`](/docs/using-the-qa-cli#email-when-the-runs-end) to turn it off.

</details>

## Start CI jobs and open your tools {#integrations}
The sidebar's **Integrations** menu (hover it to open it) has what your project added: links to reports, docs and dashboards, badges like the pipeline status, CI jobs (GitHub Actions workflows, GitLab CI manual jobs, Jenkins builds) and webhooks that call other tools. Click a job or a webhook to start it for this commit: a tag then shows whether it's pending, running, successful or failed. Click the tag to open the job's page and its logs.

<Shot
  id="integrations/menu"
  caption="Links to the project's reports and guides, and a webhook: after a click, its tag shows that the job is queued."
/>

<details>
<summary>Good to know about integrations</summary>

- On the commit list, integrations act on the branch you're looking at. On a commit page, on the selected commit and batch.
- You need to be signed in to start GitHub Actions workflows and GitLab CI jobs. Once a job started, its icon changes to *repeat*, to start it again.
- GitHub runs workflows on the latest commit of the branch (or on the `ref` the project chose), not necessarily on the commit you're looking at; QA-Board then follows the run you started. Workflows show the status of their latest run for the commit. Only the workflows declared in the project's *qaboard.yaml* can be seen and started.
- Statuses refresh every few seconds while the menu is open, and your browser remembers the jobs you started on each commit.
- A link is disabled when its target doesn't answer. Badges that don't load are hidden.
- With many entries, a search box appears at the top of the menu.
- If the project configured nothing, the menu shows its git host's defaults on branch pages: GitLab's pipeline status, or a link to GitHub Actions.
- Some projects show their most used integrations directly in the sidebar, outside the menu.

To configure them for a project, see [Integrations menu](/docs/triggering-third-party-tools).

</details>

## If runs don't start {#if-runs-dont-start}
The commit page tells you why, in a message above the views or in the form.

<details>
<summary>The commit's artifacts are missing</summary>

Runs start from the commit's artifacts. When some are missing, a message above the views says which ones, and when and by whom they were deleted:
- **This commit's artifacts were deleted** (or **are incomplete**, when files went missing without QA-Board knowing). If your project [configured it](/docs/storage/deleting-old-data#recreating-artifacts), **Recreate the artifacts** asks your CI to rebuild them, and redoing runs or starting a batch does it too. Otherwise, **Restore the artifacts** restores the files from the source code, but not build outputs like binaries.
- **This commit's artifacts are being recreated**: QA-Board asked your CI, with a link to follow the build. It doesn't start anything until the build is done: try again then.
- **Some of this commit's artifacts are missing**: you can still redo runs and start tuning, but the runs that need these files will fail.
- **Running tests from the web app needs build artifacts**, instead of the form: the project doesn't declare any artifacts in its *qaboard.yaml*. Ask whoever integrated QA-Board in your project, and see [Tuning from QA-Board](/docs/tuning-from-the-webapp).

</details>

Until the runs of a batch you started show up, a message at the top of the page says how it's going, e.g. **Your batch
is waiting for LSF**: see [Batches started from QA-Board](/docs/user-guide/logs#started-from-qa-board). On Kubernetes,
the batch's logs say why its pod waits, e.g. no node with a free GPU, and the runs' logs why theirs wait.

<details>
<summary>Every message of the Run Tests / Tuning form</summary>

| Message | What it means |
|---|---|
| **Sign in to start runs** | Runs started from QA-Board run as you. Once you're signed in, the form also lists the batch's tests and checks your settings. |
| **Fix this to start** | What would make the batch fail, e.g. an unknown batch, an invalid automated tuning configuration, a platform the project doesn't have. |
| **Before you start** | What to know first, e.g. missing artifacts QA-Board will restore. |
| **Tuning may not work** | The project's CI only saves artifacts on some branches, and not on this commit's: the message gives the commands to save them yourself, with `qa save-artifacts`. |
| **Runs will start on the QA-Board server** | The project has no runner for a cluster or task queue: runs execute on the QA-Board server, share its CPUs, and stop if it restarts. Ask whoever integrated QA-Board in your project to [choose a runner](/docs/runners). |
| **Why the batch has no tests**, **Check the batch files** | Under the batch: see [every problem flagged](/docs/user-guide/available-tests#problems). |
| Under the **Start** button | What's missing (a batch label, a batch with tests), parameters that are not valid JSON or a function that fails, or too many runs. |
| **Started …**, after you click | It started, and where QA-Board will email you. **Show its logs** opens the Logs view. |
| **… failed to start. Its logs say why.** | **Show its logs** opens them. |
| **No email when it ends: …** | The batch started, but QA-Board can't email you, and says why. |

</details>
